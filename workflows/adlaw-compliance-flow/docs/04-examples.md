# 使用示例

以下示例的输入均为**真实可跑数据**，结果由 `scripts/run_flow.py` 端到端实跑产生。

---

## 示例 1：初检 18 项 → 整改复扫通过（本工作流主场景）

**输入**（`examples/input.json`）：淘宝·化妆品违规文案 + 一份整改稿。

**输出**（实跑）：

| # | 步骤 | 状态 | 关键结果 |
|---|---|---|---|
| 1 | 输入校验 | ✅ | payload 完整；平台 淘宝 |
| 2 | 初检扫描 | ⚠️ 不建议上架 | 红线 14 / 警告 2 / 提示 2 |
| 3 | 整改复扫 | ✅ 整改后通过 | 红线 0 / 警告 0；复扫 1 次 |
| 4 | 汇总交付 | ✅ | 结论「通过」 |

**两遍扫描的价值**：初检告诉你「哪儿违规」，复扫确认「是否真改干净」。
只有两遍都跑过，才算完成合规闭环。

## 示例 2：只给初检稿（复扫跳过，交付「待整改」）

**输入**：

```json
{
  "platform": "抖音",
  "category": "食品",
  "text": "古法熬制红糖，补血养颜，暖宫驱寒，女生必备，纯天然无添加。"
}
```

**输出**（实跑）：

| # | 步骤 | 状态 | 关键结果 |
|---|---|---|---|
| 2 | 初检扫描 | ⚠️ 不建议上架 | 红线 2（补血 / 养颜）/ 警告 0 / 提示 2（纯天然 / 无添加） |
| 3 | 整改复扫 | ⏭ 跳过 | 未提供 revised_text，仅输出整改清单 |
| 4 | 汇总交付 | ⚠️ 待整改 | 交付结论「待整改」 |

**说明**：没有整改稿时，流程**不会**假称「通过」——如实交付「待整改」+ 整改清单。

## 示例 3：初检红线为 0（提前结束，复扫不必跑）

**输入**：

```json
{
  "platform": "天猫",
  "category": "母婴",
  "text": "婴儿纯棉连体衣，A 类婴幼儿标准，通过 GB 31701 检测。"
}
```

**输出**（实跑）：

| # | 步骤 | 状态 | 关键结果 |
|---|---|---|---|
| 2 | 初检扫描 | ✅ 通过 | 红线 0 / 警告 0 / 提示 0 |
| 3 | 整改复扫 | ⏭ 跳过 | 初检红线为 0，无需整改复扫 |
| 4 | 汇总交付 | ✅ | 结论「通过」 |

**要点**：「A 类」「GB 31701」是可验证的客观标准，不算绝对化用语 ——
这正是需要假阳性拦截的原因。

## 示例 4：输入缺失（中止，不硬跑）

**输入**：

```json
{
  "platform": "淘宝"
}
```

**输出**（实跑）：第 1 步 ❌ 中止，关键结果「缺字段: text」，
`flow_result.json` 中 `aborted: true`。
